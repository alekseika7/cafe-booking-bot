# Правила работы с проектом

Инструкции относятся ко всему репозиторию. При изменениях сохраняй согласованное
поведение бота; расширяй функциональность только в рамках текущей задачи.

## Назначение и границы

Сервис быстро создаёт одну заявку на новую дату сегодняшнего открытия или
явно заданную дату в Birch, Санкт-Петербург,
через API штатного виджета ReMarked. После результата сервис завершается.
Приоритеты — скорость, корректный выбор слота и защита от повторных заявок.
Универсальный движок для других ресторанов и форм сейчас не требуется.

## Структура проекта

- В корне из исполняемого Python-кода находится только `bot.py` — короткая точка
  входа, вызывающая `src.cli.main`. Бизнес-логику в него не добавляй.
- Код приложения находится в `src`. Разделяй модули по ответственности, когда
  это упрощает чтение; не создавай отдельный файл для каждой маленькой функции.
- Сохраняй текущие границы модулей:

| Модуль | Ответственность |
| --- | --- |
| `src/cli.py` | Аргументы, команды, настройка процесса и коды завершения |
| `src/config.py` | Чтение TOML и .env, валидация настроек и нормализация телефона |
| `src/rules.py` | Календарь, расчёт предоплаты, фильтрация и порядок слотов |
| `src/remarked.py` | Контракт API, HTTP-запросы и проверка виджета |
| `src/service.py` | Подготовка, ожидание открытия, опрос и отправка заявки |
| `src/storage.py` | Состояние заявки, атомарная запись и блокировка процесса |
| `src/notifications.py` | Уведомления Telegram |
| `src/diagnostics.py` | JSON-журнал, контекст запуска и безопасная диагностика ошибок |

- Документация, конфигурация сборки и пример настроек остаются в корне.
- Данные выполнения хранятся отдельно в `data` или указанном каталоге состояния.
  Не добавляй в Git реальные контакты, `.env` и файлы состояния.
  `config.toml` хранится в Git без персональных данных; поясняй каждый параметр
  комментарием. Шаблон окружения называется `example_env`; отмечай в нём
  обязательные и необязательные значения.

## Требования к коду

- Пиши небольшие функции с одной понятной задачей. Длинные функции разделяй
  по этапам работы; уменьшай вложенность ранними проверками и возвратами.
- Используй понятные имена, обычное оформление Python и явный поток управления.
  Комментарии должны объяснять причины и ограничения, а не повторять код.
- Отделяй расчёты и правила от HTTP, файлов, ожидания и уведомлений. Не размещай
  побочные эффекты на уровне импорта модуля.
- Сначала используй существующий код и стандартную библиотеку. Добавляй
  зависимости, классы и дополнительные слои только для конкретной необходимости.
- Проверяй конфиг и внешние ответы на границах приложения. Обрабатывай ожидаемые
  ошибки явно; не скрывай ошибку и не подменяй неизвестный результат успехом.
- При рефакторинге сохраняй CLI, формат запросов, файлы состояния и поведение
  повторного запуска. Изменение этих контрактов должно быть частью самой задачи.
- Не изменяй посторонние файлы и пользовательские настройки IDE ради оформления.

## Зависимости и запуск

- Пакетный менеджер — Poetry 2.2+. Зависимости задаются в `pyproject.toml`, точные
  версии фиксируются в `poetry.lock`; оба файла поддерживаются согласованными.
- Используй `poetry add` для изменения зависимостей и `poetry run` для запуска.
  Отдельный `requirements.txt` не нужен. Текущий режим — `package-mode = false`.
- Используй Python 3.14.x и Linux/macOS; файловая блокировка использует `flock`.
  Диапазон Python в `pyproject.toml`, интерпретатор окружения и Docker-образ
  должны соответствовать одной ветке 3.14.
- При изменении запуска или зависимостей обновляй README и Dockerfile.
  В Docker сохраняй запуск без привилегий, постоянный том состояния и репетицию
  по умолчанию. Автоматический перезапуск после результата сейчас выключен.

## Тесты

- Структура тестов повторяет структуру исходного кода:
  `src/cli.py` → `tests/src/test_cli.py`,
  `src/<каталог>/<модуль>.py` → `tests/src/<каталог>/test_<модуль>.py`.
- Проверки функций одного модуля размещай в соответствующем тестовом файле.
  Сценарии полного цикла бронирования относятся к `test_service.py`.
- Используй pytest и только тестовые функции, без классов. Имя каждого теста:
  `test_<имя функции>_<что проверяет>`, например `test_normalize_phone_rejects_invalid_numbers`.
  Для метода указывай имя метода. В тесте должны быть понятны подготовка данных,
  действие и проверяемый результат.
- Используй обычный `assert`, `pytest.raises` для ошибок и
  `pytest.mark.parametrize` для одинаковых проверок с разными входными данными.
- Проверяй наблюдаемое поведение и существенные граничные случаи. Не копируй
  алгоритм реализации в тест и не создавай пустые тестовые файлы ради симметрии.
- Общие фикстуры и переиспользуемый код размещай в `tests/conftest.py` или
  `conftest.py` ближайшего общего каталога тестов. Фикстуры получай через аргументы
  функций: не импортируй `conftest.py` и не импортируй тесты из других тестов.
- Для HTTP используй `httpx.MockTransport`, для времени — управляемые часы или
  фикстуру `monkeypatch`, для файлов — `tmp_path`. Тесты не должны зависеть
  от текущей даты, реального ожидания, сети или личных данных пользователя.
  Рабочий `config.toml` тоже не используй как фикстуру: тестовый TOML создавай
  из фиксированных значений в `conftest.py`, отдельно от пользовательских настроек.
- Автоматические тесты не создают реальные брони, не оплачивают их и не отправляют
  сообщения в Telegram. Сохраняй проверки отсутствия таких действий в репетиции.
- Тестовые зависимости добавляй в группу Poetry `test`. Сохраняй разделение
  `tests.src` и `src` при импортах и проверяй, что pytest обнаруживает весь набор.
- Ручные бенчмарки размещай в `tests/benchmarks`; отдельные тесты для них не нужны.
  Замеры реального API запускай отдельно от pytest и только по явной задаче.
  Результаты сохраняй в `reports/`; этот каталог исключён из Git.

## Базовое поведение бота

- Команды: `check` проверяет виджет и доступность API, `run` выполняет задание,
  `status` читает сохранённый результат. По умолчанию `run` работает без создания
  заявки. Отправка требует `--live`, заполненных контактов и обоих согласий.
- Контакты задаются через `GUEST_FIRST_NAME`, `GUEST_LAST_NAME`, `GUEST_PHONE`,
  `GUEST_EMAIL`, `GUEST_TELEGRAM` в `.env` или окружении. Секция `[guest]` в TOML
  не поддерживается. Загружай `.env` рядом с выбранным конфигом через python-dotenv,
  без перезаписи заданного окружения и без подстановки переменных в значениях.
  `example_env` содержит только примеры. Compose передаёт значения окружением;
  `.env` не копируется в образ. Тесты используют свои контакты и временный каталог,
  не читают пользовательский `.env`.
- TOML задаёт автоматический выбор или явную дату визита, число гостей,
  время открытия записи, окно визита и предпочтительное время. Также сохраняй
  настройки залов, посадки, лимита предоплаты и опроса.
- Нормализуй телефон в полный номер `+7…`. Учитывай уже заданный префикс:
  повторное добавление `+7` недопустимо.
- `booking.visit_date = "auto"` (или отсутствие поля) выбирает дату сегодняшнего
  открытия по московскому календарю и фиксирует её на весь запуск. Явная дата
  `YYYY-MM-DD` сохраняет прежнее поведение. Поздний запуск не переносится на завтра.
  Если новая дата — закрытый понедельник, остановись с понятной диагностикой;
  не подставляй более раннюю дату со свободными местами.
- Календарь виджета вычисляет границу как сегодня + 29 дней до 14:00 и + 30
  после; отдельного запроса списка открытых дат в виджете нет. Горизонт 30 дней
  хранится в коде, а не требуется в конфиге. Не выдавай расчёт даты или пустой
  список слотов за подтверждение публикации новой даты сервером.
- Открытие рассчитывается как дата визита минус 30 календарных дней в
  `Europe/Moscow`. По текущему контракту запуск заявок разрешён с 14:00 МСК;
  более позднее время задаётся конфигом. Часовой пояс машины не влияет на расчёт.
- Проверку виджета и подготовку соединения выполняй до открытия. Используй
  повторно HTTP-соединение; избегай лишних запросов в момент появления слотов.
  Сохраняй ограниченный опрос, `Retry-After`, таймауты и прерываемое ожидание.
- Для проверки виджета и получения токена допускаются три попытки при сетевых
  ошибках, HTTP 408/429/5xx, с паузами 250/500 мс или `Retry-After`. Учитывай
  остановку и дедлайн. Изменение виджета и ошибки формата не повторяй.
  Не распространяй эти повторы на создание заявки.
- Выбирай только нужную дату и начало визита внутри включённых границ окна.
  Приоритет: близость к предпочтительному времени, порядок залов, более раннее
  время. Учитывай число гостей и разрешения на общий стол и стойку шефа.
  Текущий обычный сценарий поддерживает 1–7 гостей и исключает понедельники.
- После окончания окна опроса прекращай попытки. При запуске после этого окна
  сохраняй `EXPIRED`, не создавая неожиданную заявку.
- До создания заявки сохраняй `SUBMITTING` атомарно с `fsync`. Не ослабляй
  блокировку общего каталога состояния и проверку сохранённого результата.
  Повреждённое состояние должно останавливать запуск, а не считаться отсутствующим.
- После `UNKNOWN` или `SUBMITTING` повторная отправка запрещена. Обрыв связи,
  `5xx` и `429` при создании заявки не доказывают, что сервер её не создал.
  Другой слот можно пробовать только после явного ответа `Slot is not free`.
  Не считай `request_id` гарантией идемпотентности сервера.
- Оплату выполняет пользователь самостоятельно по HTTPS-ссылке. Бот не принимает
  данные карты и банковские коды. Лимит предоплаты ограничивает запрашиваемую
  сумму; ссылка на оплату ещё не означает подтверждённую бронь или удержание места.
- Telegram-логин гостя — контакт для ресторана. Уведомления бота отдельно
  настраиваются через `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Ошибка уведомления
  не должна приводить к новой заявке: результат и ссылка остаются в состоянии.
- Не выводи в логи контакты, токены, платёжные ссылки и полные HTTP-ответы.
  Сохраняй приватные права доступа к конфигу и состоянию.
- Используй события из `src/diagnostics.py`: время UTC, `run_id`, этап и
  `request_id` для запросов. Логируй ошибки также до получения HTTP-ответа.
  Передавай только явно выбранные безопасные поля; не печатай текст внешних
  исключений, произвольные сообщения API или локальные переменные стека.
  Не переопределяй `mode` запуска при логировании выбора даты: используй
  `date_mode`. После ошибок чтения до конца окна сохраняй `READ_FAILED`, даже
  если ранее был успешный ответ; отсутствие мест нельзя вывести из ошибки API.
- При изменении виджета останавливай отправку до проверки контракта. Хеши в
  `src/remarked.py` нельзя обновлять вслепую. Тарифы и правила находятся в коде
  и README; при их изменении проверяй источник и обновляй соответствующие тесты.
- Реальную бронь выполняй только в рамках явной задачи пользователя на бронирование,
  а не для проверки разработки. Не обещай удержание столика до оплаты: оно не проверено.

## Проверка изменений

Основные команды из корня репозитория:

```sh
poetry env use 3.14
poetry install
poetry check --lock
poetry run pytest
git diff --check
```

Для отдельного модуля: `poetry run pytest tests/src/test_cli.py`.
После изменения логики запускай соответствующие тесты; после переноса модулей
проверяй обнаружение и выполнение всего набора. При правках только документации
достаточно проверить её соответствие коду, пути и команды. В отчёте указывай,
что фактически проверено; тесты с имитацией API не равны проверке реальной брони.
Версия сервиса задаётся в `pyproject.toml`; разделы CHANGELOG.md называются
по версии, а не по дате. При изменении поведения обновляй README (включая схему)
и CHANGELOG.md. Для
проверки Docker используй `check` и `run` без `--live`; учитывай расписание и
фиксируй, проверен ли реальный опрос, ожидание или сценарий с имитацией API.
После проверки останавливай запущенные для неё контейнеры; том состояния сохраняй.
